## Supabase replacement and revocation order

Official guidance now favors new secret/publishable keys over attempting an in-place legacy JWT-secret reset. Creating a replacement does not retire the legacy pair. Runtime `SUPABASE_SECRET_KEYS` and `SUPABASE_PUBLISHABLE_KEYS` are JSON dictionaries keyed by key name; the legacy variables still contain legacy keys. Treat application API-key migration and Auth signing-key migration as separate decisions. [API-key reference](https://supabase.com/docs/guides/getting-started/api-keys), [legacy rotation guidance](https://supabase.com/kb/troubleshooting/rotating-anon-service-and-jwt-secrets-1Jq6yd).

- [ ] **Owner dashboard:** open the confirmed project → **Settings → API Keys → Publishable and secret API keys**. Identify/create the replacement backend key and public key privately. Record names/IDs only. Do not assume that the presence of a runtime container means a particular named replacement already exists.
- [ ] **Required code preparation before execution:** use a shared, explicit named-key selection mechanism for all privileged clients, including widgets, diagnostics and the rollout helper. Parse the new runtime dictionary; do not pass the entire JSON string to `createClient`. A transitional fallback may help deployment staging but must not silently restore dependence on the compromised credential after cutover. Update local scripts without running their mutation paths. No such implementation changes were made here.
- [ ] **Authentication compatibility:** audit the pinned Supabase SDKs, raw REST fetches, function-to-function calls, cron/Database Webhooks and external workers. New API keys are not user JWTs; raw service calls need the appropriate `apikey` header. `_shared/rollout.ts` needs an explicit transport review, not just a variable rename. Preserve signed-in users' Bearer JWTs and explicit `getUser`/ownership/admin checks. Do not copy an `sb_secret` into a user-token verification path. Do not switch every function to `verify_jwt=false`; any necessary gateway change must ship with reviewed handler authentication. Paddle/Razorpay signature checks remain mandatory. [Migration guide](https://supabase.com/docs/guides/getting-started/migrating-to-new-api-keys).
- [ ] **Other dashboard inventories:** inspect **Edge Functions → Secrets**, scheduled jobs/Database Webhooks and Vault **names**, and external automation configuration. Never output SQL job commands, HTTP headers, Vault decrypted values, or key-list API responses. Remote-only functions must be covered. Do not manually overwrite platform-managed `SUPABASE_` variables as a shortcut.
- [ ] **Frontend dashboard preparation:** in **Vercel → FAQify project → Settings → Environment Variables**, prepare the public replacement for Production, Preview and any branch overrides. The existing code expects `VITE_SUPABASE_ANON_KEY`; that name can temporarily contain a publishable key if tested, or be renamed in a coordinated code change. Never put a privileged key in this variable. Check **GitHub → Settings → Secrets and variables → Actions**, repository environments, organization secrets and any other deployments for consumer names; do not add private build secrets the static app does not need.
- [ ] **Authorized deployment later:** deploy a security-only, current-schema-compatible patch of the actual production functions first, then a compatible frontend/public configuration build. The integration branch's new generation handlers depend on the pending billing migration; do not deploy the whole integration branch merely to rotate a key. Preserve widget URLs, FAQ records, provider webhooks, and existing function gateway settings until individually reviewed. Use the maintenance/drain procedure only once its production prerequisites are actually installed; it is currently local preparation, not an available remote switch.
- [ ] **Replacement-only acceptance later:** verify login/session refresh, generation, document flow, save/read/quota, existing public embeds, user isolation, contact/error handling and backend billing reads using replacement credentials and dedicated accounts. No exposed-key probes. Hosted saves/provider-side tests require separate authorization; do not create transactions as an incidental key check. Establish replacement use through deployed configuration/version evidence, not only a successful request that might have fallen back to the old key.
- [ ] **Owner revocation dashboard:** only after consumers are migrated, return to **Settings → API Keys → legacy keys controls** and deactivate legacy keys. If the UI couples anon and service-role deactivation, plan for both. A fresh backend key alone leaves the leaked JWT usable. Record deactivation and completion using control-plane status, not a request with the exposed credential.
- [ ] **Old-tab cutover:** legacy public-key requests can fail at the API gateway before the maintenance/stale-client RPC responds. Preserve/export drafts and prompt manual refresh before retirement. The new banner cannot update an old open app retroactively. Once retired, do not re-enable the compromised legacy key as a routine rollback; use maintenance and a forward fix with replacement credentials. A short controlled interruption may be necessary for old clients.

A leaked `service_role` JWT is not itself evidence that the JWT **signing secret** was disclosed. Do not rotate the Auth signing key or invalidate all user sessions simply because this token leaked. Review **Settings → JWT Keys** separately. If signing-secret compromise is established, plan new signing keys, session refresh/expiry and verifier/JWKS cache behavior before revoking the previous signing key; simply making a new signing key current is not revocation. Confirm actual hosted TTLs rather than relying on local `jwt_expiry`. [Signing-key guidance](https://supabase.com/docs/guides/auth/signing-keys).

## Google/Gemini replacement and revocation order

- [ ] **Owner dashboard:** identify every exposed key in the correct **Google AI Studio → Dashboard → API Keys** / **Google Cloud Console → APIs & Services → Credentials** project. Account/project ownership and the number of distinct exposed keys are not known from occurrence counts. Do not confuse these with Google OAuth client credentials.
- [ ] Create the replacement privately in the same intended project. Current AI Studio creates authorization keys bound to a service account and restricted to Gemini; confirm the service-account permissions, enabled Generative Language API, billing and model access. For an existing standard key, Cloud Console's key detail → **Rotate key** can create a replacement; verify restrictions rather than inheriting overly broad access. Do not guess static IP restrictions for Supabase's outbound traffic. [Gemini key guidance](https://ai.google.dev/gemini-api/docs/api-key).
- [ ] In **Supabase → confirmed project → Edge Functions → Secrets**, replace `GEMINI_API_KEY` privately during the authorized window. It wins over both fallback names, so changing only a fallback does not switch a present primary key. Remove/replace stale fallback configurations wherever they actually exist; they are missing in the current project inventory.
- [ ] Drain outstanding generation requests while keeping FAQ reads/embeds available. Ensure running generation workers have reloaded the replacement: this handler captures the key at module initialization. If necessary, refresh/redeploy the captured current-schema-compatible handler under separate deployment authorization. Do not deploy the pending migration-dependent integration as a rotation shortcut.
- [ ] Perform a bounded replacement-only generation check after authorization, including the document → generation path and the normal save flow. Keep prompts/output out of logs. Confirm fresh worker/configuration versions; a presence-only diagnostic is insufficient.
- [ ] **Owner revocation dashboard:** delete each exposed old key after replacement consumers have switched. With Cloud Console rotation, use the replacement key's **Previous key → Delete the previous key** action. For unused exposed keys, no replacement consumer is needed. Record provider deletion state and monitor usage/billing for unexpected activity; do not test a deleted/exposed key. Do not restore a compromised key to recover service. [Google rotation/deletion procedure](https://docs.cloud.google.com/docs/authentication/api-keys).

## OpenRouter replacement and revocation order

- [ ] **Owner dashboard:** open [OpenRouter key settings](https://openrouter.ai/settings/keys), identify exposed keys privately, and review their usage/activity and external consumers. Confirm deployed FAQify generation does not use a hardcoded legacy OpenRouter key.
- [ ] **If unused, the expected branch from current source:** delete/revoke exposed keys; do not create a replacement or add `OPENROUTER_API_KEY` to Supabase. Gemini-backed FAQify needs neither. Record provider revocation status.
- [ ] **If an active external/deployed dependency is found:** prepare a separately named replacement with an owner-approved credit limit/expiry, store it in that consumer's backend secret store, switch/reload that consumer and validate only the replacement, then delete the compromised key promptly. This continuity sequence must not become indefinite overlap. Do not assume the historical installer is safe to run or introduce an OpenRouter fallback as part of rotation.
- [ ] Review unexpected activity/credit use and remove obsolete stored copies. Recovery uses a fresh restricted replacement if needed, never reactivation/reuse of an exposed key. OpenRouter advises prompt deletion when a key is exposed. [OpenRouter authentication/incident guidance](https://github.com/OpenRouterTeam/docs/blob/main/api_reference/authentication.mdx).

## Completion evidence and recovery boundaries

- [ ] Keep the overlap window as short as practical. If provider evidence shows ongoing abuse, decide on immediate revocation and a controlled outage instead of waiting for zero-downtime cutover. No provider has been tested for abuse with the exposed credentials here.
- [ ] Keep replacement values in provider secret stores/password manager or protected local files outside Git (directory 700/file 600), entered privately without command-history literals, shell tracing, screenshots or chat. No replacement values were collected during this task.
- [ ] Record only provider/key IDs or names, consumer deployment versions, replacement-only check results, revocation timestamps/status and unresolved consumers. Missing secret names are not proof of deactivation. Audit logs and usage should remain private; report aggregates only.
- [ ] Preserve backups and FAQ/embed compatibility; pause writes if recovery is needed. Redeploy compatible code using replacement credentials, not a captured deployment containing compromised values. Keep the Paddle sandbox destination inactive; its independent signing secret is outside this incident's three credential families and was not read or changed.
- [ ] After revocation, coordinate Git history/tags/forks/archive/build/log cleanup. Current-source removal does not erase past copies, and history rewriting is not credential revocation. Do not run destructive cleanup or push without separate authorization.
