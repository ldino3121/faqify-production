# FAQify Admin Control Center rollout (review branch)

This branch is prepared from production commit `8dc3ad62fd585f3c31e03503086ae452402bfd51`. It is **not deployed to production**. Paddle stays in sandbox and the working Gemini credential is unchanged.

## Confirmed checkout warning

`create-paddle-checkout` previously called `faqify_require_sandbox_member` before looking for a checkout intent. A new non-allowlisted Free account therefore received HTTP 403 on the passive `pending` status check, despite having no Paddle customer or transaction. `BillingPlans` classified every such response as a status-service failure and displayed the yellow warning. Read-only production aggregates showed five Free accounts outside the one-account sandbox cohort and five Free accounts without checkout intents. An empty status now returns HTTP 200 with `pending:null` and an eligibility flag; it makes no Paddle API request. Purchase creation and recovery of an existing intent still require the sandbox cohort. The UI waits for authentication, separates eligibility from service failure, and discards stale status responses after an account change.

## Access and data

Read-only production inspection verified `carbonface99@gmail.com` as auth user `efb63f4a-dacd-4d78-a519-4f4e742ebf04` with the existing `admin` role. No email or UUID is an authorization rule in the application. The `/admin` route checks the existing `is_admin()` RPC, and every FACC Edge Function request checks the authenticated user's `user_roles` entry. The forward migration revokes old direct DML grants on `user_roles`, enables RLS on every FACC table, grants access only to `service_role`, and denies direct browser execution of FACC RPCs. Ordinary FAQify functionality remains available to the admin account.

FACC stores configuration versions, approved model catalog entries, real/simulated test evidence, an append-only configuration audit with actor, old/new layers and associated test evidence, request/attempt telemetry, and shared model circuit state. A new configuration requires successful real tests of every enabled model and the exact proposed routing chain within 24 hours, tied to the reviewed adapter/prompt revision. Short or failed output is not passing evidence. Emergency restore is limited to a previously active configuration. Attempt telemetry stores provider/model, returned model version when supplied, result category, latency, token counts and a price-based estimate. It stores no prompt, source URL, customer text, uploaded document, generated answer, key or raw provider response. Request/attempt and test rows are pruned after 90 days; configuration and audit history are retained. Server aggregate queries return metrics rather than customer records.

## Metric definitions and limits

All range filters use UTC `[start,end)` and the UI labels UTC explicitly. The default excludes admin accounts, sandbox-cohort accounts and manual/health tests; the operator must opt in to those categories. For billing, the default also requires `paddle_payments.environment='live'`. FACC does not treat sandbox purchases as live revenue.

| Metric | Definition |
| --- | --- |
| Total/new accounts | Profiles created before range end / inside range, after exclusions. |
| Active users | Distinct accounts with a generation ticket or credit-usage ledger entry in range. This is recorded activity, not a session count. |
| Paying/repeat purchasers | Distinct users with a completed, verified Paddle payment in range / at least two such payments in range. |
| Completed purchases, pack sales, collected totals | Completed Paddle payment rows, grouped by pack and currency. Totals are Paddle recorded minor-unit amounts and can include tax. They are not net proceeds or profit. |
| Adjustment events | Counts by action and resolution. The current adjustment table has no refunded amount; no refund value is invented. |
| Successful/failed generation | Ticket statuses recorded in the selected range. Pre-ticket failures are tracked only by new FACC telemetry. |
| Generated pairs | Length of successful ticket FAQ arrays in `completed` or `saved` state. Saved pairs and credit consumption come from usage ledger deductions, split by bucket. |
| AI request success rate | Successful completed FACC customer requests divided by completed successful or failed FACC customer requests. Started/stale requests are shown separately in System Health. |
| Provider failures and fallback | Attempt categories and distinct FACC requests with a fallback attempt. They are separate from final request failure. |
| AI latency and cost | p50/p95 of tracked request/attempt durations and estimated USD from reported input/output tokens at catalog prices. Missing usage produces unknown cost; estimates exclude unreported attempts and account-specific pricing. |

Provider attempts, fallback, token use, precise AI costs and pre-ticket failures are **tracked only after this migration**. FACC displays its first telemetry timestamp and does not backfill invented historical values. Current tables do not contain Paddle settlement fees, tax-exclusive revenue, refund amounts, or a durable webhook failure queue, so those figures remain unavailable. The health page can count processed webhook events delayed more than 15 minutes, but it cannot see an unrecorded delivery failure. Open checkout intents are local state; the page does not claim they are remote Paddle state. Existing saved FAQ rows are not used as a proxy for historical generated pairs.

## Approved routing and operating cost

The migration seed proposes `gemini-2.5-flash` then `gemini-2.5-flash-lite`; deploying it is blocked until read-only verification confirms the current runtime selections match. The optional third layer is `deepseek-flash`, disabled until `DEEPSEEK_API_KEY` is installed server-side and real compatibility tests pass. Model IDs and JSON support were checked against the [Google model catalog](https://ai.google.dev/gemini-api/docs/models), [DeepSeek pricing/model catalog](https://api-docs.deepseek.com/quick_start/pricing/) and [DeepSeek JSON mode](https://api-docs.deepseek.com/guides/json_mode/). Current catalog estimates use [Google paid standard text prices](https://ai.google.dev/gemini-api/docs/pricing) of USD $0.30/$2.50 per million input/output tokens for Flash and $0.10/$0.40 for Flash-Lite. DeepSeek uses the documented peak cache-miss estimate of USD $0.30/$1.20; actual off-peak or cached rates can differ. The admin UI identifies these as estimates with source/update date.

Both Gemini layers retain bounded retry, provider retry hints, output validation and reservation cleanup. Routing snapshots one configuration version per request. A shared Postgres circuit table coordinates repeated failures across Edge workers. Safety blocks and invalid output do not fall through to another provider. Authentication/quota errors skip the broken provider. A 120-second overall deadline covers all provider layers after request admission. Failed generation releases the generation ticket's reservation; no credit is charged until the existing atomic save succeeds.

Admin real tests use a fixed synthetic corpus, two requested pairs, a database-enforced ten-tests-per-admin-per-hour limit and no customer ticket or credits. The complete-chain test makes real calls and is distinct from the simulated fallback test. The daily GitHub Actions monitor, once enabled, checks approved model listings and makes one bounded synthetic generation probe per enabled model. It uses existing GitHub Actions/Supabase infrastructure and introduces no external monitoring service. It does add provider calls and small telemetry storage; using a 1,000-input/500-output-token illustration, a Flash probe is about $0.00155 at listed paid rates and Flash-Lite about $0.00030, before account-specific pricing. Failed retries can cost more. Monitor for actual spend before enabling DeepSeek or increasing probe frequency.

Provider aliases can change behavior without a FACC config version change; record returned model/version when the API supplies it. Check [Google's model documentation](https://ai.google.dev/gemini-api/docs/models) and [DeepSeek's documentation](https://api-docs.deepseek.com/) for retirement announcements manually. The monitor detects repeated failures and recovery but does **not** automatically read provider announcements or promote an unknown model.
